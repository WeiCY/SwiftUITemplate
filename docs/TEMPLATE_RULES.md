# 模板开发规范

> 适用范围：个人开发、2～10 人小团队、中小型 SwiftUI 项目。
>
> 目标：让新项目可以快速接入、风格统一、长期维护、逐步演进。
>
> 这份规范不是为了把模板做成“大而全”的基础库，而是为了保证它始终是一个**好起步、好维护、好扩展**的工程底座。

---

## 1. 设计总原则

### 1.1 快速接入优先

任何新增设计都必须先回答：

- 是否能缩短新项目接入时间？
- 是否能减少接入时的判断成本？
- 是否能让默认路径更容易开始开发？

如果答案是否定的，先不要加入模板主干。

### 1.2 默认值必须稳定

模板里的默认配置必须满足以下条件：

- 大多数个人 / 中小项目可直接使用
- 不需要为了开始开发就做大量改动
- 不会因为一处修改影响太多模块

### 1.3 文档必须先于扩展

当一个能力已经存在，但使用方式不够清晰时，优先补文档，不优先继续扩功能。

### 1.4 只做可复用的抽象

抽象必须来源于重复使用，而不是来源于“看起来优雅”。

---

## 2. 项目定位规则

### 2.1 适用场景

本模板适合：

- 个人 App 开发
- 小团队协作开发
- 中小型业务 App
- 需要统一技术风格的 SwiftUI 项目

### 2.2 不作为主要目标的场景

本模板不优先面向：

- 超大型组织的统一 SDK
- 多业务线平台级框架
- 需要大量定制化平台能力的复杂基础设施

### 2.3 成功标准

一个合格的模板，应该满足：

- 新项目能快速起步
- 常用能力开箱即用
- 结构清晰，不需要反复猜测
- 后续增加业务功能时，不需要重构主干

---

## 3. 分层规则

### 3.1 Core 层

`CYAppCore` 只放：

- 协议
- 基础工具
- DI 抽象
- 状态模型
- 日志
- 缓存
- Keychain
- 权限
- 网络协议
- Mock 实现

不应放入：

- 具体业务页面
- 依赖某个 App 场景的 UI
- 只能在某个项目里使用的逻辑

### 3.2 Network / Image / Persistence 层

这些层只负责“具体实现”，不负责定义模板主规则。

- `CYAppNetwork`：网络实现
- `CYAppImage`：图片加载实现
- `CYAppPersistence`：持久化实现

### 3.3 UI 层

`CYAppUI` 负责：

- `AppState`
- Router
- 反馈视图
- 启动页 / 引导页
- 统一的页面级 UI 逻辑

### 3.4 DesignSystem 层

`CYAppDesignSystem` 只负责风格表达：

- 颜色
- 字体
- 间距
- 通用组件

不在这里放业务逻辑。

### 3.5 项目结构规则

模板目录结构应保持稳定，默认遵守以下约定：

- `Sources/`：只放源码，按模块拆分
- `docs/`：只放文档，不放实现代码
- `ExampleApp/`：只放示例入口和演示代码，等主干稳定后再重点完善
- `Package.swift`：只负责声明产品、目标和依赖关系
- `README.md`：只做入口页，不承载详细实现说明

如果目录职责发生变化，必须同步更新 `README.md`、`ARCHITECTURE.md` 和接入文档。

## 4. 接入规则

### 4.1 必须有最小接入路径

模板必须提供一条“最短可运行路径”，包括：

- 引入哪些包
- `App` 初始化怎么写
- 必要配置怎么放
- `RootView` 怎么挂
- 路由和反馈层怎么接入

### 4.2 模块分为三类

#### 必选
- `CYAppCore`

#### 推荐
- `CYAppUI`
- `CYAppDesignSystem`
- `CYFeedbackStyle`

#### 按需引入
- `CYAppNetwork`
- `CYAppImage`
- `CYAppPersistence`

### 4.3 接入复杂度控制

新项目第一次接入时，不应出现以下情况：

- 需要翻多个文档才能启动
- 需要理解大量模板内部细节才能跑起来
- 需要改模板源码才能完成基础接入

---

## 5. 代码规范

### 5.1 命名规则

- 所有公共类型优先使用 `CY` 前缀
- 类型命名要清楚表达职责
- 避免同一概念在不同模块里使用不同命名

### 5.2 状态管理规则

#### 全局状态放 `CYAppState`
适合放：

- 主题
- 语言

用户、登录状态、业务 Tab 和引导完成状态属于宿主 App，不进入模板默认 `CYAppState`。

#### 页面状态放 ViewModel
适合放：

- 列表数据
- loading
- error
- 搜索关键词
- 表单输入

### 5.3 错误处理规则

以下情况不能静默吞掉：

- Keychain 保存失败
- 缓存写入失败
- 网络请求失败
- 初始化异常

必须能被上层感知、记录或处理。

### 5.4 默认行为规则

默认行为应尽量做到：

- 可用
- 直观
- 不需要额外配置就能工作

如果默认值不适合大多数场景，应通过配置覆盖，而不是强迫修改源码。

---

## 6. 文档规则

### 6.1 README

README 只做入口页，应回答：

- 这是什么
- 适合谁
- 为什么用
- 如何快速接入
- 去哪里看更详细的说明

### 6.2 GETTING_STARTED

这份文档只负责“从零接入”。

应该包含：

- 安装步骤
- 启动配置
- 最小示例
- 常见配置项
- 最常用模块示例

### 6.3 ARCHITECTURE

这份文档只解释设计理由。

应该回答：

- 为什么这么分层
- 为什么这样做 DI
- 为什么这么管理状态
- 为什么这样设计网络和反馈

### 6.4 ROADMAP

路线图必须可执行，不写空泛愿景。

每个阶段都应该写清楚：

- 做什么
- 为什么做
- 完成标准是什么

### 6.5 REVIEW

评测文档必须与当前代码保持一致。

如果代码变化较大，应同步更新评测结论。

---

## 7. ExampleApp 规则

ExampleApp 不是随便堆按钮的展示页，而是模板的“接入范例”。

### 必须展示的内容

- 基础路由
- 全局状态
- 反馈层
- 常用交互
- 真实的页面结构

### 建议展示的内容

- 主题切换
- 语言切换
- 网络请求
- 错误态
- 空状态
- 列表 / 详情 / 设置页结构

### 目标

别人看到 ExampleApp，就应该知道“这个模板在真实项目里怎么用”。

---

## 8. 变更规则

### 8.1 新增能力前先问三个问题

1. 它是否能提升快速接入？
2. 它是否会破坏默认稳定性？
3. 它是否会增加学习成本？

### 8.2 优先级顺序

1. 接入体验
2. 默认行为
3. 文档一致性
4. 示例完整度
5. 测试覆盖
6. 新功能扩展

### 8.3 不建议的改动方式

- 一次性大重构
- 一次性加入太多新模块
- 为了“更高级”而引入额外复杂度

---

## 9. 测试规则

### 9.1 重点测试方向

优先测试：

- 核心协议行为
- 网络请求关键路径
- 缓存和 Keychain
- 路由和状态管理
- 示例页最基础流程

### 9.2 测试目标

测试不是为了追求数字，而是为了保障：

- 接入不容易坏
- 默认行为不容易退化
- 后续改动不容易破坏已有能力

### 9.3 单例规则

可变单例需要考虑测试隔离，避免测试之间互相污染。

---

## 10. 发布与维护规则

### 10.1 版本节奏

- Patch：修复问题
- Minor：新增能力，保持兼容
- Major：破坏性修改，必须有迁移说明

### 10.2 文档同步

每次发布前必须检查：

- README 是否准确
- 接入文档是否准确
- 架构文档是否准确
- 路线图是否仍然成立

### 10.3 模板维护原则

模板本身要尽量稳定，业务差异通过：

- 配置
- DI
- 注入
- 扩展

来解决。

---

## 11. 代码审查标准

当检查模板代码是否符合规范时，按以下顺序判断：

1. 是否有明显违背分层的代码
2. 是否存在静默吞错
3. 是否破坏了快速接入
4. 是否让默认行为变复杂
5. 是否导致文档和代码不一致
6. 是否让 ExampleApp 失去示范价值

---

## 12. 结论

这套规范的目标只有一个：

> 让这个 SwiftUI 模板始终保持“适合个人和中小团队，能快速接入、统一风格、长期演进”的状态。

如果某个改动不能帮助这个目标，就不应该优先进入模板主干。
